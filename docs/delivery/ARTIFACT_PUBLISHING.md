# Artifact Publishing

Status: approved direction. **The subsystem this document describes now lives in KAE-Artifacts, not in Studio.**

## What changed, and what Studio still owns

This document was written when generation and publication were going to be Studio's delivery subsystem. They are now a separate component — [KAE-Artifacts](https://github.com/crismag/KAE-Artifacts) — which is implemented, tested, and callable over HTTP.

Almost everything below still holds. The principle, the publisher abstraction, the three targets, the GitHub branch-and-draft-PR workflow, the "never write to the default branch" rule, the credentials-never-in-the-browser rule: all of it was right, and all of it exists. What changed is **which repository holds the code**.

| Concern | Owner now |
| --- | --- |
| Choosing what to generate, and letting a user edit that choice | **Studio** — the plan is a resource it can `PATCH` |
| Showing proposed changes and taking approval | **Studio** — the surface; KAE-Artifacts supplies the preview and records the approval |
| Generation, validation, packaging | KAE-Artifacts |
| Publisher implementations and provider concurrency | KAE-Artifacts |
| What the project knows, and which revision produced an artifact | KAE-Memory |

Two things KAE-Artifacts settled that this document left open, and Studio's UI should follow them rather than the sketch further down:

**Approval binds a preview, not a package.** A user approving "four files" has not been told whether those files are being created or overwritten. The preview carries a per-file outcome — add, modify, unchanged, conflict — and the approval is evidence bound to that exact preview, the package checksum, the destination and the destination's state at review time. A boolean "approved" flag is not enough, and is no longer accepted.

**A stale approval is refused, not reconciled.** If the target branch moves between review and publication, publication fails with `stale_base` and writes nothing. The UI needs a path for this: it is an ordinary outcome, not an error state to apologise for.

**Not yet wired.** Studio does not call KAE-Artifacts today, and KAE-Artifacts has no HTTP client adapter for GitHub or S3. Both are named tasks; neither is done.

## Principle

> Project artifacts are generated once; each project selects where they are published.

The destination does not change the meaning or structure of the generated artifact.

```text
Project memory
    -> Context assembler
    -> Artifact generator
    -> Artifact bundle
    -> Selected publisher
```

```text
ArtifactPublisher
├── GitHubPublisher
├── LocalWorkspacePublisher
└── S3Publisher
```

Publishers are interchangeable implementations of one interface: validate the target, compute proposed changes against current target state, apply after review, and report result or conflict. No generation logic lives in a publisher, and no publisher-specific shaping leaks into generation.

## Targets

### 1. GitHub repository

The user connects or selects a target repository. Studio writes the package tree beneath the configured target directory.

Workflow:

```text
Generate artifact
    -> show proposed changes
    -> user reviews
    -> create branch
    -> commit files
    -> optionally open draft PR
```

KAE-Studio must not normally write directly to the default branch. Direct default-branch writes require explicit per-project opt-in and are recorded as such.

GitHub credentials live in AWS or the installed agent environment — never in the browser frontend.

### 2. Local workspace through an installed agent

When KAE-Studio is available as an agent tool or connected to a local companion:

```text
KAE-Studio
    -> local agent/tool
    -> approved workspace
    -> project files
```

This enables direct creation or update of paths such as `/home/cris/workspaces/MyProject/docs/requirements/`.

The browser frontend cannot write to arbitrary local directories. A local agent, CLI, IDE extension, MCP tool, or desktop companion performs the filesystem operation.

The local tool must:

- restrict writes to an approved project root;
- show proposed files or changes before applying;
- preserve unrelated files;
- detect existing Git changes in the workspace;
- use patches for updates rather than wholesale overwrite;
- report conflicts;
- optionally create a branch and commit.

### 3. S3 artifact storage

The managed destination when no repository or local workspace is connected.

```text
KAE-Studio
    -> AWS API
    -> artifact generation
    -> S3
    -> controlled download
```

S3 stores the generated bytes. CockroachDB stores artifact metadata:

```text
artifact_id
project_id
artifact_type
version
content_hash
storage_target
storage_reference
source_memory_revision
generated_at
generation_status
```

S3 may also act as temporary staging for all generated artifacts regardless of final destination. It must not become the authoritative project copy when a repository is the designated target.

## Project destination configuration

```ts
type ArtifactTarget =
  | {
      type: "github";
      repository: string;
      baseBranch: string;
      targetDirectory: string;
      publishMode: "branch" | "draft-pr";
    }
  | {
      type: "local";
      workspaceId: string;
      targetDirectory: string;
    }
  | {
      type: "s3";
      bucketAlias: string;
      targetPrefix: string;
    };
```

Never store a raw local path as though AWS could reach it. A `workspaceId` refers to a workspace registered with the local agent; the agent resolves it to a filesystem path on its own side. Likewise `bucketAlias` is a server-side reference, not a bucket name chosen by the browser.

## Precedence

The destination is selected explicitly per project. Default proposal when unset:

1. Connected GitHub repository → propose branch or draft-PR publication.
2. Connected local agent workspace → propose local file changes.
3. Neither available → store the versioned package in S3 and offer download.

## UI implications

A project destination control:

```text
Project Output

● GitHub repository
  crismag/example-project
  Directory: docs/kae/
  Publish through: Draft pull request

○ Local workspace
  Connected agent required

○ Managed download
  Stored securely in S3
```

The Deliverables screen distinguishes **Generated**, **Reviewed**, **Published**, **Outdated**, and **Conflict** (defined in `CONTEXT_PACKAGE.md`), and shows where each version was published.

## Boundary

KAE-Memory remembers what artifact was generated, which knowledge revision produced it, where it was published, its content hash, and which requirements and evidence support it.

KAE-Memory does not own GitHub commits, filesystem writes, or S3 transfer implementation. Those belong to KAE-Studio's delivery subsystem.

## Revised end-to-end flow

```text
Discovery and meetings
    -> Structured project knowledge
    -> Module-level definition
    -> Reviewed deliverable
    -> GitHub, local workspace, or S3
    -> Development begins
    -> Changes return to KAE-Memory
```

This is what allows KAE-Studio to be both a hosted SaaS and an installed development agent without two product models.

## Security

- Publishing credentials are held by the server or the local agent, never the frontend.
- The local agent enforces its own approved-root restriction; it does not trust a path supplied by the server.
- Publication is an outward-facing action: it requires user review and confirmation, and each publication is audited with actor, target, version, and content hash.
- A conflict never resolves by silent overwrite.
